# AIchat-graph 协作思考

让讨论留下可理解、可继续的实体思考图。
Agent 维护 Markdown 节点和关系，实时界面跟进讨论，独立 HTML 用于回顾。

| 场景 | 读取 |

## 讨论与记录

- 聊天中完整回答当前问题，讲清必要的概念、理由、条件和例子。
  不能用“已记录到图中”代替解释，也不机械复述全部旧节点。
- 先处理用户正在讨论的问题。沿用已确认的要求，不反复当作候选征求认可。
  文件维护不应把交流变成批准继续、等待更新和阅读维护汇报。
- 节点聚焦一个明确问题或认识，并能脱离当轮聊天独立阅读。
  概述说明要点；正文保留必要解释、实例条件和证据；有共识时记录认可范围与限制。
  具体写法见内容维护参考，不以压缩篇幅或固定模板代替准确表达。

## 启用与绑定

- 用户启用指定工作区的图记录后，在本对话范围内持续按需维护；暂停记录时停止写入。
- 从用户给定信息、已配置命令或宿主实际加载的入口确定 CLI 和工作区。
  工具源码目录、讨论工作区与当前 shell 目录分别核对，不猜目录。
- 用户可给主题名、目录、续谈节点，或前端“复制给 Agent”的定位信息。
  首次用 `topics` 核对实际主题，绑定工作区和稳定 topicId；唯一匹配后持续沿用。
  重名或目标不明时只澄清真实歧义。新聊天不自动创建新主题。
- 用户明确换主题才切换本对话的记录目标。
  前端浏览选择、全局 activeNode 和其他聊天的焦点都不替代绑定。
  可以为比较而跨主题读取，但不建立跨主题父边或默默改写对照主题。
- 初始化、服务启动、安装、迁移与批量提炼沿用具体授权，Skill 不自行授予这些操作。

## 图的含义

- **主题**组织一个可持续的问题，每个主题有独立根；节点不等于聊天消息或任务。
  同一节点可多轮完善，一轮也可维护多个节点。
- **next**沿当前线索向下继续；**branch**展开可独立返回的方向。
  全局主线在最左侧，分支向右、同源分支上下组织，局部 next 仍纵向推进。
  按内容关系选连接，节点位置、间距和编号交给程序处理。
  `side` 不控制当前前端的左右落点，不为外观调整结构字段。
- **description**解释为什么从来源接到目标，用短关系句，不重复两端标题。
  长理由写正文；改接来源后重写对应关系说明。
- **proposed / agreed / reference**分别表示提议或待确认判断、用户明确认可的内容、
  资料与一般解释。认可不等于已执行、实测或掌握；新提议不继承来源的 agreed。
- **important**是节点的回看标记，用 `important` 命令维护。
  **lastChanges[topicId]**是图接口中每主题最近一批内容修改，普通节点读取不返回。
  两者不是同一项元数据，也不表示完整历史。
- Markdown 是维护源，HTML 是自动生成的只读成品。
  读取和修改实体记录，不从庞大的 HTML 恢复正文，不手动双写成品。

## 每轮按需维护

先判断本轮是否产生值得保留的认识、理由、条件、实例、修正或可返回的方向。
没有实质变化可以不写，也不要求每轮必须调用工具。

1. 在绑定主题内定位相关内容。陌生主题先读概览；已知节点可直接读正文。
   搜索限定 `--topic`，修改前理解相关正文与相邻关系，不只凭摘要覆盖解释。
   小改动不必读取全图；只改元数据或取凭据时可用 `--meta`。
2. 同一问题的补充优先原位完善；后续问题用 next，独立侧面用 branch。
   不按聊天时间一路串 next，也不为展示横向结构机械建 branch。
   同一轮既补充旧问题又记录新问题时用 batch，一次提交；已在链中的常见插入用 insert，
   不先建旁支再重排。确有需要时可拆分、整合正文并重排，保留必要理由、条件、实例与稳定 ID。
   现有节点的批量重连用 rearrange 表达最终关系，不制造临时旁支。
3. 普通纠错可覆盖；重要判断改变时保留理解当前认识所需的来路。
   改 state 时同次同步概述、正文和共识；局部认可不扩大为整张卡已确认。
4. 在答复结束前完成必要维护并核对结果，保存失败或未解决的冲突须说明。
   托管写入已经校验结构，不例行重复全图验证或运行开发测试。
   直接编辑源文件、出现诊断或怀疑损坏时，再按实际授权和问题检查。

不制造空节点、日期流水、逐轮副本、固定“已更新”汇报或额外状态文档。
保存成功后自然继续讨论，后续读取按实际需要进行。

## CLI 关键边界

- 使用服务同版本的 CLI 和 Skill，始终显式传 `--workspace`。
  新对话从可见入口确认位置，不依赖上一聊天的隐藏记忆；接口或构建版本用 version、whoami 核对。
- 读取可直接选择 overview、structure、content，不强制逐层访问。
  程序负责整次预算和分页；将 `page.next` 原样交回 `--cursor`，不手算各卡偏移。
  正文标题定位用 `--from-heading`，同名标题序号用 `--occurrence`（0 起）。
- 写入凭据统一在读取或写入结果的**顶层 `refs[nodeId]`**；命令参数只接收其中的 token 字符串。
  离线读取的 refs 为空，不能写入。不要再从 item.editRef、result.editRef 或 editRefs 取凭据。
- 同一轮补充旧问题并记录新问题用 batch；链中插入用 insert；两者都是一次事务。
  batch 的局部名称只在本输入有效，不能当稳定 ID 或凭据；结果看 created.aliases 与顶层 refs。
- 哈希与身份由工具核对。冲突后重读并重新判断，不自动补新哈希强行提交。
  结果未知时先用原 requestId 查询 `status` 并核对源内容，不盲目换 ID 重发。
- 长正文用文件或 stdin；正文替换、追加和局部替换三种模式互斥。
  参数、batch 结构、提交状态与错误处理见命令参考，不凭记忆编造选项。
- 服务不可达时可以离线读源并继续讨论，清楚说明尚未保存的部分。
  用户特别提出附件需求时再处理，不预建附件库、备份系统或知识库双写。

Skill 是行为指引，不是自动注入每轮回复的后台钩子。
