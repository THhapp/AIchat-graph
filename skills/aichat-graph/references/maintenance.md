# 节点内容与维护分寸

首次组织主题、编写概述／例子／共识或遇到记录尺度问题时阅读，读过后按实际讨论沿用。操作参数见[命令速查](commands.md)。

## 聊天与节点都应可理解

聊天承载当前交流所需的完整解释，节点承载值得长期保留、可返回继续的内容。不能只回复“解释见节点”，也不要求聊天机械复述整个主题。
节点可以重组、去重和消除现场指代，但不能把必要解释只留在聊天，或把用户当前需要理解的内容只写进图。

## 节点该承载什么

一个节点聚焦一个明确的问题或认识。保留理解所需的条件、理由、推导、例子与证据；出现可独立讨论的方向时再考虑分支，避免在卡片内部堆叠多条未展开的议题。
必要解释较长仍可留在同一节点，不能为了短小而删去适用条件，也不按段落或字数强制拆卡。无需每张卡填满同一组栏目，有共识时使用下面规定的共识小节。

标题用具体问题或概念，不用日期、“本轮更新”或与状态重复的“已确认”等提示。正文可有必要的 Markdown、代码、公式、表格和列表，不假定原始 HTML 或脚本可以执行。

读者应能脱离当轮聊天理解：把“上面第二个”“这个”换成明确对象，保留实例初值、环境条件和适用范围。实验记录区分给出代码、用户已运行、实际观察、解释和尚待验证的猜想。状态不能代替事实证据。

## 概述与正文

主动编写概述，先告诉读者节点回答什么、核心认识或仍在讨论的要点是什么。概述不是标题复述、正文目录或无条件的结论，也不能把未确认的提议写成定论。
使用现有 `summary` 字段；未显式设置时程序取正文首段并截短，因此新节点的正文首段先写有意义的概述，避免摘要变成问候、维护过程或冗长背景。
已有节点可用 `edit --summary` 明确设置概述。创建入口不接受该参数时不硬加：首段足够表达就沿用派生概述，确有需要再通过实际读取凭据补设。
正文保留理解所需的解释、条件、代码、公式和例子，不因图上只显示概述就删除这些内容。修改要点或适用范围时核对显式概述；没有显式概述时核对首段是否仍准确。

例如，标题“展平后的维度”不足以交代内容；概述“对每个样本的 `[16,4,4]` 特征图，展平得到 256 个特征；批次维度保留”给出核心关系与条件。正文再解释各维度与乘积，不泛化成任何输入都得到 256。

## 具体例子与一般论述

外部具体例子使用独立 Markdown 引用块，块首标明“具体例子”或“临时参考”，注明可核对的来源，例如用户材料名称、文件定位或实际来源链接。
通用观点与推理写普通正文；另行交代该例子说明什么、有哪些限制，不把一次观察当作普遍结论。自行构造的例子说明是假设或示意，不伪称用户已运行或来自外部资料。
引用块用于区分材料，不必逐字引用整篇原文；缺少来源时如实说明，不编造出处。不为引用块另造程序专用字段或 HTML 样式。

## 已形成的共识

节点确有明确共识时，正文设置 `## 已形成的共识`，完整记录与该节点有关的结论、成立条件及排除项；标题层级按正文结构调整。
没有明确共识时不加空小节，不把所有节点都当成必须填满的模板。无需为得到共识频繁要求用户确认普通说明。

- 以用户明确表达或确认的内容为依据；“继续”、没有反对、Agent 的推荐或程序检查通过都不自动表示认可。
- 提议、参考材料与待验证解释在相应内容中保持原性质，不混进共识。状态标签不能替代正文中的具体约定。
- 共识变化时原位更新相关条目；重要改变保留必要理由，不保留每轮措辞副本，不把整个主题共识复制到每个节点。
- “认可解释”“同意采用方案”“用户已执行”“观察到结果”“用户已掌握”分别表达，不由其中一项推定其余各项。

## 原位、后继与分支

| 讨论变化 | 做法 |
| --- | --- |
| 同一问题补充解释、条件、例子或修正 | 原位完善 |
| 沿当前线索进入后续问题 | next；来源已有后继时先理解结构，不插队覆盖 |
| 有独立讨论价值的对照、假设、启发或侧向问题 | branch，并说明从来源展开的理由 |
| 一轮澄清了当前主题内多个已分开的思考单元 | 分别维护相关节点，不强行合成一张 |
| 解释较长，但仍是同一问题 | 保留必要解释，不单纯按长度拆卡 |
| 看好某方向但暂时没有精力实现 | 保留关注理由和可返回的问题，不自动变成开发任务 |
| 同意继续、重复表达或无实质变化 | 不必制造节点或更新 |

分支不以分歧为唯一条件。也不要求每次答复只落一处，或把所有 AI 联想都记入图。

先问：新内容是在补全现有回答、沿当前线索进入后续问题，还是换到一个可单独返回的侧面？
连接按这个语义判断，不按聊天时间、内容长度或泛泛的“更深入”判断。不为平衡左右空间或改善外观而改写 next／branch；编号和自动布局仍由程序派生。

例如，已有节点讨论卷积与池化后的张量尺寸，用户困惑展平后为何是 256：在明确实例参数后，补充 `[N,16,4,4]` 与 `16×4×4=256` 的联系，通常原位完善即可。若转向“改变输入分辨率后如何设计全连接层”，可另开分支。不能丢掉条件只记“展平是 256”，也不必复制整轮问答。

## 整体整理与重连

除了原位补充和后继生长，也可以按内容关系拆分、合并、移动和重连已有节点——前提是结构比现在更清楚，而不是更好看。这不需要用户每轮批准，但只在本次讨论确实需要改善结构时做。

整理前：读相关正文和直接相邻节点，确认这些内容属于同一主题，不把别的主题的论证并进来；先想清目标结构（哪些卡保留、谁接谁、谁作为下一张）。

整理时：保留必要的理由、条件、实例与共识；合并是去重而不是删掉适用条件，拆开后每张卡的概述仍能独立说明自己的问题，不把同一结论复制到多张卡；改动连接就重写 `description`，旧描述解释的是旧边。不无故更换稳定 nodeId，前端定位和历史引用依赖它。

整理后：核对概述、正文、共识与连接描述是否一致；用 `read <topicId> --view structure` 核对最终结构与编号是否仍成立，怀疑结构损坏时再用 `validate`。不把“允许整理”变成每轮重排全图。

已有节点的整体重排用 `rearrange` 一次表达最终关系；它会保留来源唯一 `next` 的约束，占用目标位置的后继要纳入同一次整理。参数与边界见[命令速查](commands.md#整体整理与重连)。

## 更新与保留来路

普通纠错、措辞改善可直接覆盖。重要判断改变时，判断覆盖后是否还看得懂为什么走到现在；必要时保留原判断的关键理由、改变依据及当前认识。不机械保存每版全文，不新建历史主题或备份目录。

未采纳、未实施和暂时不研究的方向可以有价值，但不必全部保留；以以后能否回顾、继续为判断，不以是否完成为标准。

不把同一结论复制到多个节点，不记录维护日志、日期流水或空的占位卡。

## 连接与状态

`description` 回答“从 A 为什么接到 B”，既不是目标摘要，也不自动声称因果或证明。改接来源后重新检查描述。
写成短关系句，通常以 8—20 个可见字符为写作尺度，不机械凑字或作为程序硬限制；只保留辨认这条关系所需的意思，长理由写节点正文，不把两端标题或完整摘要再复述一遍。
例如“从固定尺寸延伸到可变输入”能说明来路；仅写“展开”过于空泛，长篇复述前后讨论也不适合作为连接文字。需要缩短时重写核心关系，不能简单截字丢失含义，也不另建第二份关系说明。

- `proposed`：提议或尚未确认的判断。
- `agreed`：用户明确确认的对应内容；不能用一声“继续”认可整组假设。
- `reference`：资料、外部证据与一般解释；事实依据仍需准确。

AI 的建议不自动成为共识。认可解释不等于实际执行，实际执行不等于结果已验证，更不等于用户已掌握。
状态对应节点的主要判断或方案；用户只确认其中一条条件或局部约定时，不据此把整张节点升级为 `agreed`，在共识小节准确记录认可范围即可。不要为了让整张卡只有一种认可程度而机械拆卡。

## 有变化时核对什么

先判断状态是否真的变了：用户明确确认这条判断才升为 `agreed`，普通纠错、补充例子通常只改文字。状态和文字在同一次编辑里改完：改 state 就同步概述、正文与共识中的对应表述，不能让已确认的原则继续留在旧候选句里；只认可其中一部分时，正文分开写“已认可”和“仍未定”，不把局部认可写成整条结论。

维护本次涉及的节点时，检查正文是否完整准确、概述是否仍代表当前内容、共识及限制是否跟上变化、连接描述是否仍解释真实来路，现行状态是否与表达相符。
这是同一次编辑中的一致性判断，不要求重新阅读全图、运行全套测试或额外建立检查表文件。没有实质变化可以不写，保存失败或冲突未解决则明确说明。

## 记录与提炼

图可保留具体实例、疑问和思考联系。长期知识 Markdown 按需要另行提炼，不每轮双份维护，也不为每个节点建立对应知识笔记。

提炼去掉现场指代和维护过程，保留独立理解所需的条件、机制和例子；不把候选判断或未运行代码变成已证实事实。
