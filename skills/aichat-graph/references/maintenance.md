# 节点内容与维护分寸

首次组织节点、编写概述／例子／共识或整理结构时查阅，之后按实际讨论沿用。
操作参数集中在[命令参考](commands.md)，本页说明内容判断，不维护第二套命令表。
本页是 Skill 的协作方法；程序负责结构、版本、事务和呈现，不自动判断共识或执行这些写作约定。

## 聊天与节点都应可理解

聊天提供当前交流所需的完整解释，节点保存值得回顾和继续的内容。
不能只回复“解释见节点”，也不要求聊天机械复述整个主题。
节点可以重组、去重和消除现场指代，但必要解释不能只留在聊天里。

优先回答用户正在问的问题，沿用已经确认的要求。
维护文件不应让用户陷入批准继续、等待更新和阅读维护汇报的循环。
必要的解释充分准确，不设置强制短回复、固定字数或每轮工具次数。

## 节点该承载什么

一个节点聚焦明确的问题或认识，保留条件、理由、推导、例子与证据。
出现可独立返回的方向时再考虑分支；解释较长本身不是拆卡理由。
不按段落或字数强拆，也不要求每张卡填满同一套栏目。

标题用具体问题或概念，不用日期、“本轮更新”或与状态重复的“已确认”。
正文可使用必要的 Markdown、代码、公式、表格和列表，不假定原始 HTML／脚本会执行。

将“上面第二个”“这个”等现场指代换成明确对象，保留实例初值、环境和适用范围。
实验内容分别表述给出代码、用户已运行、观察到结果、解释与待验证猜想。
状态标签不能替代事实证据。

## 概述与正文

概述说明节点回答什么、核心认识或尚在讨论的要点，不能只是标题复述或正文目录。
没有确认的提议仍保持提议语气，不为得到一句“结论”而删掉限制条件。

使用现有 summary 字段；未显式设置时，程序从正文首段派生并截短。
新节点的首段先写有意义的概述，避免问候、维护过程或冗长背景占据预览。
创建入口支持 --summary，确有需要时在创建时一次给齐，避免创建后再单独 edit 一次。

正文保留完整理解所需的条件、机制、推导与例子。
更新核心认识时同步核对显式概述；没有显式概述时核对首段是否仍准确。

例如，标题“展平后的维度”，概述可写：
“每个样本的 [16,4,4] 特征图展平为 256 个特征，批次维度保留”。
正文说明各维度和乘积，不能泛化为任意输入都得到 256。

## 具体例子与一般论述

外部具体例子使用独立 Markdown 引用块，块首标明“具体例子”或“临时参考”，
注明可核对的材料名称、文件定位或实际来源链接。
一般论述与推理写普通正文，另说明这个例子能支持什么、有哪些限制。

自行构造的例子说明是假设或示意，不伪称用户已经运行或来自外部材料。
引用块不必逐字复制原文，缺少来源时如实说明，不编造出处。
不为引用块另造程序字段或专用 HTML 样式。

## 已形成的共识

确有明确共识时使用“已形成的共识”小节，保存相关结论、成立条件和排除项。
通常用 `## 已形成的共识`，标题层级按正文结构调整。
没有共识不加空小节，也不为了填模板频繁索要确认。

- 以用户明确表达或认可为依据；“继续”、没有反对、AI 推荐或程序通过不自动表示认可。
- 资料、提议和待验证解释保留原性质，不混入共识。
- 共识变化时原位更新，重要改变保留必要理由，不保存每轮措辞副本。
- 不把整个主题的共识复制到每张卡。
- 分别表述认可解释、采用方案、已执行、结果已验证和已经掌握，不互相推定。

## 原位、后继与分支

| 讨论变化 | 做法 |
| --- | --- |
| 同一问题补充解释、条件、例子或修正 | 原位完善 |
| 沿当前线索进入后续问题 | next；已有后继时先读结构，不覆盖插队 |
| 可独立返回的对照、假设、启发或侧面 | branch，并说明来路 |
| 一轮澄清多个已有思考单元 | 分别维护相关节点，不强合成一张 |
| 同一轮补充旧问题并记录新问题 | 用 batch 一次提交，避免最近更新只剩后一批 |
| 解释较长但仍是同一问题 | 保留必要解释，不按长度拆卡 |
| 看好某方向但暂时没有精力实现 | 保存关注理由和可返回的问题，不自动变成开发任务 |
| 重复表达、同意继续或无实质变化 | 可以不写 |

分支不以分歧为唯一条件，也不要求每次答复只落在一个节点。
先判断新内容是在补全现有回答、进入后续问题，还是展开可独立返回的方向。
不按聊天时间、篇幅或泛泛的“更深入”判断，也不为节点摆放改写 next／branch。

例如，已有节点解释卷积和池化后的尺寸，用户追问为何展平后是 256：
在明确参数后补上 [N,16,4,4] 与 16×4×4=256 的联系，通常原位完善即可。
若转向“改变输入分辨率后如何设计全连接层”，再建立分支。
不丢掉条件只记“展平是 256”，也不逐句复制问答。

## 整体整理与重连

内容关系确有需要时，可以拆分、整合正文、移动和重连，不局限于一路追加。
这一授权不等于每轮重排全图，也不允许为了外观重写语义。

整理前读取相关正文和直接相邻关系，确认主题边界，再想清目标结构：
哪些节点保留、内容如何分配、最终谁接谁。

整理时保留理由、条件、实例和共识；合并内容是去重，不是删掉适用条件。
拆开后各卡的概述仍能独立说明问题，不复制同一结论，不无故更换稳定 ID。
连接改变时重写 description，不能残留只解释旧边的说明。

只重连已有节点时使用 rearrange，完整声明占位后继的最终去向。
参数见[最终入边重排](commands.md#rearrange只表达最终入边)。
同时涉及正文、创建或连接的整理可用 batch；内容取舍仍由 Agent 判断。
rearrange 不附带正文整合或删除，高层命令也不提供自动删除或语义合并。
能力边界见[不支持与边界](commands.md#不支持与边界)。

整理后按需要读取 structure，核对最终结构和编号，怀疑损坏时再 validate。
同一轮补旧问题并提出新问题时，分别放回相关位置，不把全部内容倾倒进最新节点；需要一次提交时用 batch。

## 更新与保留来路

普通纠错和措辞改善可直接覆盖。重要判断改变时，保留理解当前认识所需的原理由、
改变依据与现有认识，不机械保存每版全文，也不新建历史主题和备份目录。

未采纳、未实施或暂不研究的方向可以有价值，以以后能否回顾和继续为保留依据。
不把所有联想都记下，不重复结论，不制造维护日志、日期流水或空占位卡。

## 连接与状态

description 回答“从 A 为什么接到 B”，不是目标摘要，也不自动声称因果或证明。
通常以 8—20 个可见字符作为短句写作参考，不是程序硬限制，不机械凑字。
只保留辨认关系所需的信息，长理由写正文，不复述两端标题或另建一份关系说明。

例如“从固定尺寸延伸到可变输入”说明来路；仅写“展开”过于空泛。
需要缩短时重写核心关系，不截字丢失含义，也不因前端能够折行而写成长段说明。

- proposed：提议或尚未确认的判断。
- agreed：用户明确确认的对应内容。
- reference：资料、外部证据与一般解释，事实依据仍须准确。

状态对应节点的主要判断或方案。只认可某条条件时，在正文准确记录范围，
不能据此将整张卡升级为 agreed，也不为了单一认可程度而机械拆卡。

## 本次维护的一致性

先判断认可范围是否真的变化。普通纠错和补例子通常只改文字。
改 state 时，同一次编辑同步概述、正文与共识中的对应表述；
局部认可则分清“已认可”与“仍未定”，不让标题和正文相互矛盾。

检查本次涉及的内容是否完整准确、概述是否代表当前认识、共识和限制是否同步、
连接说明是否仍解释真实来路、状态是否与表达相符。
这是同一次编辑中的判断，不要求扫全图、跑全套测试或新建检查表文件。
保存失败和未解决的冲突必须说明，成功后自然继续讨论。

## 记录与提炼

图保留具体实例、疑问和思考联系；长期知识 Markdown 按需要另行提炼。
不要求每节点配一份知识笔记，也不每轮维护两份相同正文。
提炼去掉现场指代和维护过程，保留条件、机制和例子，不把候选或未运行代码写成实证。
