# 节点内容与维护分寸

首次写节点或整理结构时查阅，之后按实际讨论沿用。
本页负责内容判断和写作约定；操作参数见随附的[命令参考](commands.md)。

## 什么值得入图

保存有助于日后理解问题、作出选择或继续探索的内容：目标、认识、关键取舍及理由、
必要证据，以及有价值的疑问和未实现方向。图的完整性以思考可追踪为准。

记录价值取决于主题目标。任务派发、工具调用、常规进度和验收流水通常留在聊天中；
过程揭示重要限制、改变认识或影响结论与复现时，提炼必要部分融入对应节点。
同一段代码可能只是实现细节，也可能是学习内容；不按内容形式一律排除。

一次回复可以没有图修改，也可以维护多张卡。按内容价值自主判断，不逐条请求记录许可；
未入图的临时过程不必转存另一份文档，工程文档只保留继续开发、运行和维护所需信息。

## 内容落点

一张卡片回答一个明确问题，不承载整个主题。判断新内容是否仍在回答原卡的问题，
而不是只看是否属于同一主题、是否篇幅较短。

| 讨论变化 | 处理方式 |
| --- | --- |
| 补充原问题的理由、条件、实例或纠错 | 原位完善 |
| 原问题形成结论或改变理解 | 原位完善认识及理由 |
| 出现值得独立返回的后续问题 | 新建 next |
| 出现值得独立返回的方向、对照或假设 | 新建 branch |

原位更新把补充融入对应位置，删去失效或重复叙述；
避免按轮次在末尾叠加重复的更新小节。
相关的条件、理由与证据放在一起，把一个问题表达完整；不按篇幅或措辞变化机械拆卡。
有价值的未决或未实施方向可以保留，是否新建以内容关系和后续可继续性判断。

## 体量与概述

| 部分 | 常规写作预算 |
| --- | --- |
| 标题 | 通常 8–24 字，直接指出问题，不重复既有标记或正文标题 |
| 图上概述 | 30–60 字，最多 80 字 |
| 正文 | 通常 150–400 字，常规上限 600 字，含必要的例子与依据 |

按中文阅读量估计，短内容不凑数。超限先精简重复叙述和空泛过渡，
再判断是否存在独立子问题；必要的连续推导、代码、公式可例外保留，仍控制阅读体量。
这些是 Skill 的节点写作约束，不是程序源格式校验，也不限制聊天解释所需的长度。

概述说明当前认识或尚待判断的核心，不复述标题或罗列正文目录。
使用显式 summary 字段；未设置时从正文首段派生并截短。
清除显式摘要用 summary:null，CLI 对应 --clear-summary。
正文首段直接说明当前认识或问题；概述与正文各有作用，不要求逐字重复。
修改核心认识时同步概述；需要显式概述时可在创建或本次修改中一起提交。

## 正文格式

按下列顺序选用需要的二级小节，名称保持一致，不留空栏目；短卡可以只有首段。

| 可选小节 | 何时使用 |
| --- | --- |
| `## 说明` | 需要展开条件、理由、机制或推导 |
| `## 例子` | 具体实例有助于理解 |
| `## 选择与依据` | 重要取舍及其理由需要单独展开 |
| `## 待讨论` | 有值得继续判断的具体问题 |

例子不是必选项，其他小节也不为填模板而添加。
实例放在“例子”小节，用普通段落、列表、代码或表格；逐字引用原文时才用 >。
外部材料注明实际来源，自拟实例标明是假设或示意。
按需给出理解实例所必需的初值、环境和适用条件，不伪称已经运行或观察到结果。

正文保留支持当前认识的条件、理由和证据，现场指代改为明确对象。
需要时写清实际选择、适用条件和具体疑问，建议与实测结果按事实表述。
普通卡片无需登记是否认可、实施或掌握，也不把确认标签改写成逐卡维护的文字。
原始 HTML／脚本不会执行，使用正常 Markdown、代码、表格和公式表达即可。

## 整理与保留来路

普通纠错可覆盖。重要认识改变时，保留理解当前认识所需的原理由和改变依据，
不保存每版全文、日期流水或逐轮副本。修改依据实际读取的内容与版本；
已有上下文和写回的 nodeRevisions 可直接沿用，需要理解新变化或发生冲突时再读。

整理随正在修改的内容进行，清除重复与失效过程；出现跨卡重复或关系不清时再扩大范围，
不要求每轮重读全图，也不按节点数量定期压缩。
整理前理解相关正文和邻接关系，确定内容分配与最终结构，保留稳定 ID。
拆分、整合和重连保留必要条件、理由、证据与重要选择，不为外观改写语义。
补充融入对应位置，按需使用完整 body 或局部 replace；append 只负责末尾追加，不会自动融合正文。
description 解释为什么从来源接到目标，通常以 8–20 个可见字符作为短句参考，
不是程序硬限制；长理由写正文，改接后同步说明。

只重连已有节点用 rearrange（最终入边一次提交）；
同时涉及正文、创建或连接的修改用 batch，链中插入用 insert，删除无子节点叶卡用 delete。
高层命令不自动语义合并或递归删除；具体边界见[命令参考](commands.md)。
补旧问题并在后面加新问题、把一组卡片重排到最终位置都属于一次事务候选，不先写入临时旁支。

整理后确认提交结果与受影响节点，后续可沿用返回的 nodeRevisions。
出现具体失败再扩大核对，不把写入后的全图重读或测试当作固定流程。
保存值得回顾的认识与问题；独立知识文档按需提炼，不每轮双写相同正文。

## 回顾最近变化

图上的“新增／改动”和主题清单中的“删除”只描述最近一次内容批次，不是累积历史；
需要核对上一次写入具体改了什么、或确认其他 Agent 的写入影响时，用 diff 看字段与正文差异。
普通续谈不必先看 diff；预览批量修改只在需要先确认时使用，不把预览当固定步骤。

## 参考依据

以下用于理解记录取舍，不是每次记录前的必读材料。

- [Andy Matuschak：原子笔记](https://notes.andymatuschak.org/Evergreen_notes_should_be_atomic)：
  围绕一件事并表达完整，过度碎片化也会损害关联。
- [Michael Nygard：架构决策记录](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)：
  借鉴重要选择的背景、理由与后果，不照搬确认状态和固定模板。
